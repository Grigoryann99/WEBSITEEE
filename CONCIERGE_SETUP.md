# Local concierge implementation

This work is local only. Do not push this branch or deploy to Vercel without the owner's separate instruction.

## Available without external account setup

- `/destinations/italy/rome`: filters in the URL, place sheets, attributed media and a synchronized Leaflet map.
- `/destinations/italy/rome/gifts`: estimated gift budgets, quantities, shop shortlist and geographic stop ordering.
- `/plan`: editable preview, day assignment, drag handles and keyboard move buttons, group budgets and same-day combined ticket handling.
- A persisted display currency, validated upstream rates, browser last-good cache and a bundled dated fallback.
- Basic consent gating: optional Google scripts load only after acceptance; preferences can be reopened in the footer.
- `/guides`, `/stay`, `/destinations/[country]` replace the old locations with permanent redirects. Existing content is retained.

## Supabase activation

1. Use a project owned by the site owner, preferably a separate test project first.
2. For a fresh project, run `node scripts/prepare-supabase.mjs`, then paste `supabase/setup-new-project.sql` into the project's SQL Editor and run once. It creates all eight private tables in one transaction and refuses to run if any application table already exists. Alternatively, apply migrations `0001_concierge.sql`, `0002_custom_requests.sql`, and `0003_revoke_table_management.sql` in order; do not use both installation methods. Do not run against unrelated tables without reviewing the schema.
   If the first two migrations or the earlier two-migration setup bundle were already applied, run only `supabase/migrations/0003_revoke_table_management.sql`. It removes excess TRUNCATE, REFERENCES and TRIGGER grants from the eight application tables without deleting data or changing normal user operations. Then repeat the verification query. Hosted execution is not confirmed until those results are checked.
   Keep Data API enabled, automatic table exposure disabled and automatic RLS enabled. The SQL explicitly grants only the application permissions it needs. Run `supabase/verify-setup.sql` afterwards: expect eight `setup_ok=true` rows and two function rows with member execution allowed, guest execution denied and an empty search path. This checks configuration, not actual cross-user behavior.
3. Configure `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` locally. No service-role key is required by this implementation.
4. Configure the chosen Google, Apple and Azure providers in Supabase and their own consoles. Add the local `/auth/callback` and eventual production callback to the allowed application redirects.
5. Set `NEXT_PUBLIC_AUTH_PROVIDERS` to ONLY the providers actually configured, e.g. `google`. Restart/rebuild after changing public environment variables.
6. Create two test users. Run `supabase/tests/ownership.sql` with the fixture UUIDs in an isolated database. Verify save/load, sign out, session refresh and profile currency across devices. The migration has not been executed or RLS-tested against a hosted project during offline development.

Account records, trips, saved places, private conversations and custom-plan requests use the signed-in user's publishable-key client and RLS. Child trip items and messages are guarded through their parent ownership. Saving a trip uses an atomic invoker RPC.

## Groq activation

Set `GROQ_API_KEY` server-side and select a currently available compatible `GROQ_MODEL`. No provider keys are exposed to the browser. `/api/concierge` checks authentication, same-origin requests, body size, hourly database quota, response shape, catalog IDs, repeated attractions and daily duration bounds. AI returns IDs only; venue facts are rendered from the catalog.

`/concierge` is the conversational interface. `/api/concierge/guide` answers using the selected country guide or Rome catalog, includes bounded conversational history, requires account sign-in and consumes the same hourly quota. Reference ids are validated against that destination; answer text is generated by the model, so the UI explains that guides may be incomplete or outdated. These chats currently remain in the tab and are not inserted into legacy Rome threads. Rome AI itinerary generation is preserved at `/concierge/itinerary?destination=italy%2Frome`.

Provider defaults are centralized in `lib/ai-config.ts`. The current local configuration uses `openai/gpt-oss-20b` with low reasoning effort. `node scripts/probe-concierge-guide.cjs` performs one live public-guide smoke request; `--models` reads the provider's available model ids. Neither prints credentials.

The model's travel time approximation is not a routed itinerary. Prices and hours in the initial dataset are not independently verified. Concierge output and user requests are saved to that user's private conversation tables.

## Payments and commercial activation

`/plan/custom` saves a request for a written quote, without charging a payment or claiming a booking. Requests are stored in `custom_plan_requests`; there is no staff notification workflow yet. A payment provider, agreed prices, delivery terms and partner accounts are required before implementing or advertising paid checkout. Existing venue links go to the official provider and do not claim affiliate earnings unless actual partner links are supplied and marked.

## Checks

- `npm run check:concierge`
- `node node_modules/typescript/bin/tsc --noEmit --incremental false`
- `npm run build`
- Run the production server, then `node scripts/check-canonicals.mjs http://localhost:3000`.
- Run `node scripts/check-concierge-http.mjs http://localhost:3000` for redirect headers, request-origin guards, unauthenticated access and rates.
- Check desktop/mobile, map movement between selected places, filter URL reload, modal keyboard focus, currency persistence, consent rejection and preview budgets.

## Remaining production gates

- Hosted Supabase and OAuth setup; actual two-user RLS and auth tests.
- Groq credentials and real-provider response tests.
- Payment provider / partner IDs / service terms; staff notification and operational handling of custom requests.
- Review all Rome facts and media. Some photos are illustrative and some are intentionally omitted; missing images use an explicit placeholder. Automatic Wikipedia selection has excluded known logo/coat-of-arms entries.
- Dependency security remediation remains necessary for the inherited Next.js 14 stack before production release; this change does not claim to resolve all existing npm advisories.
- ExchangeRate-API data updates daily. The persistent browser cache survives a return visit; a server restart falls back to the bundled snapshot if the upstream is unavailable. There is no shared server-side last-good store yet.

Secrets belong in local/server environment configuration, not in source, chat or Git. Start only with the data access the feature requires.
